## 网上课程参照与游戏化修订

按用户后续意见，主线修订为“成熟课程的教学结构 + 软件项目模拟游戏”。下面是公开页面调研后的提案，尚未实现。只查看了公开课程大纲与制作案例，没有声称看完收费课、登录课程或复用受限素材。

### 主要参照

1. **University of Alberta — Software Product Management**：主参照其流程、需求、规划、评审到综合项目的连续结构。大学官方介绍明确将综合项目放在模拟软件生产情境中。其制作团队 Onlea 介绍了 Conversation Simulator 和 Release Planning 工具，适合参考交互形式，不照搬原题、角色、视频或脚本。
   - https://www.coursera.org/specializations/product-management
   - https://www.preview.ualberta.ca/en/admissions-programs/online-courses/software-product-management.html
   - https://onlea.org/software-product-management/
2. **Client Needs and Software Requirements（同系列）**：公开大纲依次为需求入门、用户互动、需求编写、需求质量；包含用户故事、验收测试、待办列表、原型及作业。先借它校正需求模块的知识覆盖和练习难度，不把几次选对话选项当成完整课程。
   - https://www.coursera.org/learn/client-needs-and-software-requirements
3. **IBM — Introduction to Software Engineering**：补足产品管理系列不能替代的技术基础，例如生命周期、开发角色与环境、编程基础、架构与设计。参考其讲解、阅读、实验、测验与最终项目的组织方式；网页没有真实视频时不做虚假的视频播放器。
   - https://www.coursera.org/learn/introduction-to-software-engineering

### 游戏提案：《开发工作室：第一次上线》

学习者担任小型开发团队的新人负责人，接到校园活动报名项目。校园系统是游戏中的交付对象，不是额外要求学习者独立写一整套生产系统。游戏采用轻量网页项目工作台：客户消息、任务看板、项目预览、测试与日志。沿用 Forma 现有浅色外观；先不引入 3D 场景、人物养成、资产商城等无关开发量。

课程保留独立知识章节和查阅入口，不要求学完每章进入游戏。已有“上线挑战”和“编程闯关”已归入独立游戏入口，原路由和已有记录保留。

| 游戏章节 | 学习内容 | 玩家真正要操作的东西 | 反馈依据 |
| --- | --- | --- | --- |
| 接到委托 | 需求获取与需求类型 | 向模拟客户追问，区分事实、功能与约束 | 提问揭示了哪些信息，仍有哪些未知 |
| 明确交付 | 用户故事、验收条件 | 补全报名规则，判断重复报名、满额、取消等边界 | 验收规则能否被具体用例检验 |
| 排首版 | 优先级、依赖、估算 | 拖动功能卡，安排迭代，说明暂缓项 | 公开的模拟容量和依赖约束，而非随机扣分 |
| 搭系统 | 职责、接口、数据与权限 | 补全请求流程、数据关系和权限规则 | 是否存在漏校验、越权或状态矛盾 |
| 处理变更 | 迭代与协作 | 客户加功能时重新协商范围，处理评审意见 | 变更影响是否说明，原验收条件是否仍满足 |
| 测试救火 | 复现、定位与回归 | 从日志和输入找 bug，补测试，修一小段代码 | 固定用例的真实结果，不修改断言掩盖错误 |
| 发布值班 | 配置、部署与回滚 | 评审发布证据，在错误配置事件中恢复服务 | 模拟发布检查、故障原因及恢复证据 |

每个任务都应具备：先前置讲解、示范一个相似问题、明确目标、允许尝试、具体反馈和复盘。自由文本评价与客观规则分开；AI 可做提示或对话，但通关不依赖它任意给一个“满意度”。时间/预算数值应标为教学模拟参数，不伪装为真实预测。失败可撤回重试，记录学习证据而非羞辱性惩罚。

### 第一个可试学版本

只做“接到委托 → 明确交付 → 排首版”这一小段，配套需求类型、有效访谈、用户故事、验收条件和范围取舍的原创讲解。示例事件：客户要求一次上齐聊天、支付、推荐和报名，但交付时间有限。玩家应追问实际目标，并根据给定证据决定首版，而不是靠猜制作人的唯一选项通关。

验收重点是：换一个需求场景后，学习者是否能写清规则、解释取舍，并从反馈中修正。先让用户试玩确认趣味和教学深度，再扩展技术、测试与发布章节。以下原始主线和六课样板保留作为知识内容底稿，不再作为纯阅读式项目的最终产品形态。

## 现有问题（本次阅读判断）

- 现有课程正文大量是约 100–350 字的案例短文。以 `curriculum.js` 中“跟踪一次请求”为例，正文约 296 字；它提出了服务端校验与权限边界，却没有带学习者查看具体请求、响应、状态变化或完成一次追踪。短不是错误，缺少足够的教学展开才是问题。
- 各课交替使用二手书、预约、失物认领、售票、订餐等案例，学习者容易反复适应背景，难以感受上一课的成果在下一课发挥作用。
- 已有目标、示例答案、workshop 和课后练习链接，不应全盘否认已有结构。但仍需把讲解、完整示范、练习、反馈真正连成一条线，而非靠链接拼接。
- 编程题、工具实验与概念课的粒度不同；需要明确本节练什么、是否需要代码、按什么检查，而不是统一用泛化反思题收尾。

## 软件工程主线

建议先制作一门完整主课《从 0 做完一个软件项目》，而非扩充大量浅层课程卡片。以“校园活动报名系统”为贯穿案例：学生找活动、报名、取消；组织者管理名额与名单。范围先不含付款、推荐或复杂社交。

| 模块 | 必须讲清的核心 | 可检查的成果 |
| --- | --- | --- |
| 系统基础 | 浏览器、服务端、数据库分别负责什么；一次请求怎样往返 | 请求过程图及可观察的请求/响应样例 |
| 需求与范围 | 用户目标、用户故事、验收条件、边界、首版取舍 | 一页需求说明和可验收规则 |
| 数据与状态 | 实体、字段、关系、约束；报名/取消/满额状态 | 简单数据模型、状态图与规则 |
| 设计与接口 | 职责划分、接口约定、失败响应、权限检查 | 报名接口与前后端责任表 |
| 协作与实现 | 任务拆分、提交、分支、评审；小步完成变更 | 一次可复核的小功能交付 |
| 测试与排错 | 正常/边界/失败情况、复现、定位、回归；区分单元与集成 | 测试清单、失败用例和修复证据 |
| 发布与维护 | 构建、配置、密钥、部署、日志、监控与回滚 | 上线检查单和故障处理记录 |

概念如用户故事、状态图、数据约束、接口、测试层级，先直观讲解、再引入正式术语；不能只让学生“注意边界”“提供证据”。项目制不等于只讲故事，也不能省掉理论。

## 每节的教学结构

1. 一个具体问题，先说明本节会学会什么、需要哪些前置知识。
2. 用通俗语言把原理讲完整；图、表、代码只在有帮助时使用，避免强制每课一种版式。
3. 展示一个完整示范，解释每一步为什么这样做，并比较一个错误或替代方案。
4. 学习者完成一个小变体：补规则、排步骤、改接口、修代码或验证结果；不反复写泛泛感想。
5. 反馈指出具体哪条规则/哪个测试未满足，提供定位提示、分级提示与参考解法，允许重试。
6. 收尾说明这节产物怎样被下一节使用；提供简短总结和可选深入阅读。

建议每节约 10–15 分钟作为初始编排目标，发布前根据实际试学调整，不再根据字数随意声称学习时长。不能把“已阅读”“已提交”和“已掌握”混成一个状态，也不默认强制锁住后续课节。

## 三类课程的定位

- 软件工程：主线项目 + 必要理论；优先做深。
- 编程基础：按语言独立学习路径，分清首次接触者与已有经验者；不要要求零基础同时学五种语言。主线项目的代码练习可先用现有浏览器 JavaScript 环境，减少编译下载的干扰。
- AI 与开发工具：Git、SQL、Docker、CI/CD、AI 辅助等作为按需补充课；主线用到时链接到相应工具课，不提前堆满术语，不把认识按钮当成学会工程实践。

## 第一批只做一个样板模块

建议先重做“需求与范围”，用六节串起来：

1. 从“我要一个报名网站”中找出具体问题。
2. 设计能问出真实过程的访谈问题。
3. 从访谈记录区分事实、需求、假设。
4. 写清楚一条用户故事。
5. 把“可以报名”改成能测试的验收规则。
6. 在时间限制下决定首版范围，并提交一页需求说明。

样板必须同时完成课程页、完整示范、至少一种有效练习及具体反馈。验收重点：不看答案能否解释规则、完成新情境的小变体，并知道自己错在哪里。先让用户试学确认风格和深度，再扩展其余模块；不一次性生成几十节模板课。

## 保留与迁移

旧课程、课节 ID、笔记、收藏和完成记录先保留。正式重做前设计新旧映射；必要时将旧内容标为旧版，而非直接抹掉。知识练习与主线概念一一对应，编程练习与具体技能对应，实践实验承接工具操作；AI 面试保持独立。数据表和账户系统另行确定，本方案不预建关联关系。
